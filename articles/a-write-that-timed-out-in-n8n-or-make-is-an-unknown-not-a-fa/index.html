A write that timed out in n8n or Make is an unknown, not a failure: look it up before you resend

2026-11-09

A question on the n8n forum on 08.11.2026: a workflow sends a write to an external API and the call times out. The write may have gone through, but the lookup still says "not found" because reads lag, and the API has no idempotency keys. What do you wait for before sending it again? The same week, a Make user had a CRM "create" module that returned a 504 after about 30 seconds even though the record was created, so every retry risked a duplicate.

The forum replies already have the right rule: a timeout means you don't know what happened, not that it failed. Here's how I'd wire that rule in both tools, then a full worked case with one API I use a lot (starting an Apify Actor run from n8n). It's a good example because the API gives you everything you need to settle the question without guessing.

First, stop the tools from resending for you

Both tools can resend a write on their own before your logic gets a say.

  • n8n: "Retry On Fail" in a node's settings reruns the node after any failure, timeouts included. Leave it on for reads. Turn it off on any node that creates or charges something, and set "On Error" to "Continue (using error output)" so the timeout goes into a branch you control.
  • Make: per Make's help page on automatic retries, RateLimitError, ConnectionError and ModuleTimeoutError can produce incomplete executions that Make retries by itself, up to 8 times (1 min, 10 min, 10 min, 30 min, 30 min, 30 min, 3 h, 3 h, so about 8 hours in total), *starting from the module that failed*. If that module is a create, each retry is a resend. Put an error handler route on the create module, and make that route do the lookup described below instead of relying on the automatic retry.

The pattern for any API

1. Write down what you're about to send, before you send it. A row in a sheet or a database table: your own reference (form submission ID, order ID, anything stable), the payload, the time, status = pending.

2. If the API lets you store that reference in a searchable field, include it in the write. That's what makes the lookup exact later on.

3. Timeout = still pending. Wait longer than the API's read lag before you look. If "not found" 10 seconds later is normal for that API, checking after 10 seconds tells you nothing. I check after 2, 5 and 15 minutes.

4. Found exactly one match → mark it done and carry on with the existing record's ID.

5. Not found after the last check → resend once, and only once.

6. Two matches, or a lookup that itself fails → stop and send it to a person. Don't create anything else.

The weak spot is step 2. If the API has no field for your reference, you end up matching on content (same email, same amount, within a few minutes of each other), and that can't separate two genuine identical requests. When that's the case, I'd rather send ambiguous cases to a human than resend automatically.

Worked case: starting an Apify run from n8n

A lot of n8n workflows call Apify's run-sync-get-dataset-items endpoint from an HTTP Request node: one POST, and the dataset rows come back. Apify's API reference says that if the run takes longer than 300 seconds, the response is a 408. Apify's academy page on running Actors through the API adds that the response then describes the run with status RUNNING. In other words, your HTTP call gave up but the run didn't, and it keeps using (and billing) compute. The same page suggests restarting the run asynchronously at that point. I'd look for the existing run first: restarting while the first run is still going means paying for two runs.

The cleaner setup avoids the long call altogether. Every request is short and the run ID is in your hands from the start:

1. Set node before the call: sentAt = {{ $now.minus({ seconds: 5 }).toUTC().toISO() }} and input = the JSON you're about to send.

2. HTTP Request: start the run (Retry On Fail off, error output on)

POST https://api.apify.com/v2/acts/OWNER~ACTOR-NAME/runs?waitForFinish=60&maxTotalChargeUsd=2
Header: Authorization: Bearer <your Apify token, stored as a Header Auth credential>
Body (JSON): {{ JSON.stringify($json.input) }}

waitForFinish is capped at 60 seconds. If the run finishes in that time, you get it back with its final status. If not, you still get the run object with its id and defaultDatasetId. maxTotalChargeUsd caps what that single run can be charged, which also caps the damage if a duplicate slips through.

3. Poll, success branch. GET https://api.apify.com/v2/actor-runs/{{ $json.data.id }}?waitForFinish=60, followed by an IF node: while data.status is READY or RUNNING, loop back. Cap the loop (for example 30 rounds = 30 minutes) and alert someone if the cap is reached. When the status is SUCCEEDED, read GET https://api.apify.com/v2/datasets/{{ $json.data.defaultDatasetId }}/items.

4. Lookup, error branch. This only runs if the start call itself didn't answer:

  • Wait node, 2 minutes.
  • GET https://api.apify.com/v2/acts/OWNER~ACTOR-NAME/runs?desc=1&limit=20&startedAfter={{ $('Set').first().json.sentAt }}. Per the API reference, the list is filtered on start time, and each item has id, status, startedAt, meta.origin and defaultKeyValueStoreId.
  • IF node: if data.items is empty, no run started. Go to the "not found" path (check once more after 5 minutes, then resend once). Otherwise, Split Out on data.items, then one HTTP Request per candidate: GET https://api.apify.com/v2/key-value-stores/{{ $json.defaultKeyValueStoreId }}/records/INPUT. Apify keeps each run's input there, so you can compare it with what you sent.
  • A Code node ("Run Once for All Items") decides:
// Compares the stored INPUT of each candidate run with what we sent.
// Only the keys we sent are compared, in case defaults were added to the stored input.
const sent = $('Set').first().json.input;
const candidates = $('Split Out').all();   // run list items, same order as the INPUT calls
const inputs = $input.all();               // one stored INPUT per candidate

const same = (a, b) => JSON.stringify(a) === JSON.stringify(b);
const matches = inputs
  .map((it, i) => ({ run: candidates[i].json, stored: it.json }))
  .filter(({ stored }) => Object.keys(sent).every(k => same(sent[k], stored[k])));

let decision = 'resend_once';
if (matches.length === 1) decision = 'follow_run';
if (matches.length > 1) decision = 'human';
return [{ json: { decision, found: matches.length, runId: matches[0]?.run.id ?? null } }];
  • Switch node on decision: followrun goes into the polling loop from step 3 with that runId. resendonce goes back to the start node with a flag that stops a second resend (check again after 5 minutes first, as in the general pattern). human sends an alert with the run IDs. Once you've picked the run you keep, a duplicate can be stopped with POST https://api.apify.com/v2/actor-runs/RUN_ID/abort. Usage already consumed stays charged.

Limits

  • If two executions start the same Actor with the same input within the same few minutes, the stored input can't tell them apart. That's the content-matching limit from above. One fix is to give each workflow its own Apify task and list that task's runs (GET /v2/actor-tasks/TASK_ID/runs?desc=1) instead of the Actor's. Another is to queue the starts.
  • Adding a unique "reference" field to the input only works if the Actor accepts extra fields. Some input schemas reject unknown properties, so check that before relying on it.
  • I haven't checked what the 408 body of the run-sync-get-dataset-items variant contains in every case, which is why the lookup above doesn't depend on it. If your n8n HTTP timeout is shorter than 300 seconds, n8n gives up first and you get no body at all.
  • The polling loop costs one request per minute per run. That's fine for a few runs a day. For many runs, Apify's ad-hoc webhooks (the webhooks parameter on the start call) let Apify call your n8n webhook when the run ends, so you don't have to poll.
  • None of this makes a non-idempotent API safe. It only makes sure that each resend is a decision your workflow made, not something that happened by default.
