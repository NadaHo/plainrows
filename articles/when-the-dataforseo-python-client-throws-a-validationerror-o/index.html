When the DataForSEO Python client throws a ValidationError on a call you already paid for

2026-11-05

A bug report filed on 05.11.2026 against DataForSEO's official Python client (dataforseo-client 2.1.9 and 2.1.10) shows a failure mode worth knowing about if you use any strictly typed, generated API client: the HTTP request succeeds and is billed, and then the client throws while parsing the response.

The symptom

aioptimization/llmmentions/target_metrics/live raises:

pydantic_core._pydantic_core.ValidationError: 1 validation error for AggregatedMetricsItemInfo
key
  Input should be a valid string [type=string_type, input_value=2840, input_type=int]

The model types key as a strict string for every grouping, but under aggregated_metrics.location the API returns a location code, which is an integer (2840 is the United States). Under language or platform the key is a string, so those parse fine.

According to the report, a call costs about $0.10. You pay it, you get an exception, and if your code records the cost only after a successful parse, the charge never shows up in your own accounting.

A workaround you can apply today

Loosen that one field once, at startup:

from typing import Optional, Union
from pydantic import StrictInt, StrictStr
from dataforseo_client.models.aggregated_metrics_item_info import AggregatedMetricsItemInfo

AggregatedMetricsItemInfo.model_fields["key"].annotation = Optional[Union[StrictInt, StrictStr]]
AggregatedMetricsItemInfo.model_rebuild(force=True)

I tested this with dataforseo-client 2.1.10, pydantic 2.14.3 and Python 3.14, against a mocked HTTP response, not a live call:

  • llmmentionstargetmetricslive called through the client with urllib3 mocked: it fails without the patch and returns with it. location[0].key is the int 2840, language[0].key is still the string "en", and to_dict() keeps the int.
  • The same class is used by the location list of multitargetmetrics and of the four topmentioned* endpoints (brands, brand_categories, domains, pages). Parsing {"location": [{"key": 2840}]} with each of those item models fails before the patch and works after it.

You don't need to rebuild the parent models. Rebuilding the item class was enough in every case I tried.

The documentation doesn't settle what those other endpoints send either. The topmentioneddomains page types the location key as integer, but its example response shows "key": "2840" in quotes. The Union accepts both.

Or skip the models

Every endpoint method has a withoutpreload_content twin that returns the raw HTTP response:

import json

raw = api.llm_mentions_target_metrics_live_without_preload_content([request])
data = json.loads(raw.data)
cost = data["cost"]

You lose attribute access and type hints, but a schema mismatch can't stop you from reading the data or the cost. If you track spend per call, I think this is the safer default anyway: read cost from the raw JSON first, then parse into models if you want them.

Limits

  • The patch is a monkeypatch of generated code. Remove it once a fixed release is out, and pin the client version until then, because a regenerated model could be shaped differently.
  • I haven't seen a live response from these endpoints, so I can't tell you which of them really send integer keys. The patch works whichever type they send.
  • Don't retry a billed call because parsing failed. The request reached DataForSEO and was charged, so a retry costs the same again. Fix the parsing and keep the body you already have.
