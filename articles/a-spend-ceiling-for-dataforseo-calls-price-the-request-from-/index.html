A spend ceiling for DataForSEO calls: price the request from the free price list before you send it

2026-11-06

A bug report filed on 05.11.2026 against an open-source SEO command-line tool describes a guard doing its job a little too well. The user asked for search volumes on 797 keywords with a 0.20 USD ceiling. The tool refused to run ("cannot enforce spend ceiling without current pricing") even though the tool's own estimate said 0.09 USD, because it had no price snapshot loaded for that command.

I think refusing is the right default: a ceiling that guesses prices isn't a ceiling. But you don't need a manual price file to enforce one. DataForSEO gives you three pieces to work with: a free price list for your own account, a daily spending limit enforced on their side, and a cost field in every response. Here is how I'd use them together.

1. Read prices from appendix/user_data (free)

GET https://api.dataforseo.com/v3/appendix/user_data costs nothing (the response reports "cost": 0). Besides your balance and rate limits, tasks[0].result[0].price holds the price of every endpoint for your account. This is what it looked like when I called it on 06.11.2026:

"keywords_data": {
  "google_ads": {
    "search_volume": {
      "live": {
        "priority_normal": [{"cost_type": "per_request", "cost": 0.09}]
      }
    }
  }
},
"dataforseo_labs": {
  "keyword_overview": {
    "live": {
      "priority_normal": [
        {"cost_type": "per_result", "cost": 0.00012},
        {"cost_type": "per_request", "cost": 0.012}
      ]
    }
  }
}

(Trimmed: each endpoint also has prioritylow and priorityhigh.) Two things to know before you parse it:

  • Each priority holds a list of entries, not one object. Labs endpoints have two entries, a fixed price per request plus a price per result row, and you need to add them up. costtype is perrequest (per GET or POST) or per_result (per returned row; for Labs keyword endpoints that means per keyword item that comes back).
  • The tree doesn't always follow the URL. In the response I got, the endpoint /v3/dataforseolabs/google/keywordoverview/live is priced under dataforseolabs/keywordoverview/live, with no google level, while keywordsdata keeps its googleads level. Look up the paths in your own response before you hard-code them.

2. Turn the prices into a worst-case estimate

The formula:

estimate = ceil(items / max_items_per_request) × per_request + items × per_result

Use the maximum number of result rows, so the estimate is an upper bound. For keyword endpoints, that's one row per keyword you send.

  • Google Ads search volume, live: up to 1,000 keywords per request, and the docs say each request is billed the same whatever the number of keywords. 797 keywords = 1 request = 0.09 USD at the price above. 1,001 keywords would be 2 requests, 0.18 USD.
  • Labs keyword overview, live: up to 700 keywords per request. 797 keywords = 2 requests: 2 × 0.012 + 797 × 0.00012 = 0.1196 USD at most.

Here is the guard in plain Python (standard library only):

import base64, json, math, time, urllib.request

API = "https://api.dataforseo.com/v3"

def fetch_prices(login, password):
    """Free call (cost 0). Returns the price tree of your own account."""
    token = base64.b64encode(f"{login}:{password}".encode()).decode()
    req = urllib.request.Request(f"{API}/appendix/user_data",
                                 headers={"Authorization": f"Basic {token}"})
    with urllib.request.urlopen(req, timeout=60) as r:
        body = json.load(r)
    result = body["tasks"][0]["result"][0]
    return {"fetched_at": time.time(), "price": result["price"],
            "balance": result["money"]["balance"]}

def unit_prices(snapshot, path, priority="priority_normal"):
    """path like 'keywords_data/google_ads/search_volume/live'.
    Returns (per_request, per_result). Raises KeyError if the path is unknown."""
    node = snapshot["price"]
    for part in path.split("/"):
        node = node[part]
    per_request = per_result = 0.0
    for entry in node[priority]:
        if entry["cost_type"] == "per_request":
            per_request += entry["cost"]
        elif entry["cost_type"] == "per_result":
            per_result += entry["cost"]
        else:
            raise ValueError(f"unknown cost_type {entry['cost_type']!r}")
    return per_request, per_result

def worst_case_cost(snapshot, path, n_items, items_per_request):
    per_request, per_result = unit_prices(snapshot, path)
    requests = math.ceil(n_items / items_per_request)
    return requests * per_request + n_items * per_result

def check_ceiling(snapshot, path, n_items, items_per_request, ceiling_usd,
                  max_age_s=24 * 3600):
    if time.time() - snapshot["fetched_at"] > max_age_s:
        raise RuntimeError("price snapshot too old, refresh it")
    estimate = worst_case_cost(snapshot, path, n_items, items_per_request)
    if estimate > ceiling_usd:
        raise RuntimeError(f"estimate {estimate:.4f} USD > ceiling {ceiling_usd} USD")
    return estimate

I ran it against a live user_data response, which costs nothing. I didn't make any paid call. Results:

  • checkceiling(s, "keywordsdata/googleads/searchvolume/live", 797, 1000, 0.2) returns 0.09.
  • checkceiling(s, "dataforseolabs/keyword_overview/live", 797, 700, 0.2) returns 0.11964.
  • 2,500 keywords on search volume are refused: estimate 0.2700 USD > ceiling 0.2 USD.
  • dataforseolabs/google/keywordoverview/live raises KeyError: 'google'.

All of these fail closed. If the path is unknown, the cost type is new or the snapshot is old, the call doesn't go out, which is the behaviour you want from a guard. If you also want the run to stop when the account is nearly empty, compare the estimate with snapshot["balance"] too.

3. Put a hard limit on the account as well

A ceiling in your code only protects that one process. Two cron jobs, a retry loop or a colleague's script each have their own copy. DataForSEO lets you set a daily expense limit in the API Settings of the dashboard, for all APIs or for one API or endpoint. According to their help center, a request over the limit is refused with error code 40203 ("The cost limit has been exceeded"), and the limit works over 24 hours in UTC. I set it to the most I'd accept losing on a bad day, and I keep the per-run ceiling in code for the normal case.

4. Reconcile with what was actually billed

Every response has a top-level cost and a cost per task. Log the estimate before the call, then the billed cost after it, in the same place. If the billed cost ever exceeds the estimate, your price snapshot or your request count is wrong, and you want to find out on a 0.10 USD call, not a 50 USD one. Read cost from the raw JSON before anything else can throw. A parsing error after a billed call shouldn't make the charge disappear from your books.

Limits

  • The price list is for your account at the moment you read it. Prices change, and the figures above are only what one account showed on 06.11.2026. Refresh at least once a day and don't share a snapshot between accounts.
  • per_result makes the real cost depend on how many rows come back. The worst-case formula overestimates when some keywords have no data. That's the safe side, but a tight ceiling can refuse runs that would have fit.
  • A client-side check doesn't see other processes spending at the same moment. If several workers share one budget, have each one reserve its estimate in a shared counter (one database row, one Redis key) before calling, and release the difference afterwards. Otherwise rely on the account limit.
  • The daily account limit stops spending, it doesn't refund it. Everything billed before the cut stays billed.
