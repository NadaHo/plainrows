How stale is DataForSEO Labs data? Read the row dates, then refresh only what a decision needs

2026-11-08

An issue opened on 08.11.2026 in a small open-source SEO tool raises a fair worry: DataForSEO Labs (ranked keywords, competitors, domain intersection) is a database snapshot, so it can lag by weeks or months. The plan in the issue is sound: Search Console for your own site, live SERP calls for competitor positions on your target keywords, Google Ads volumes instead of Labs volumes, an "as of" date on every table, and Labs kept for discovery. A follow-up asks for an automatic status check on every URL the tool shows that isn't a live 200 page in the latest crawl.

Before rebuilding anything, I'd measure how stale the data really is. The responses already tell you, and it costs nothing extra.

How old the rows actually are

Every Labs row carries its own dates. In rankedkeywords, each item has rankedserpelement.lastupdatedtime (when that SERP was captured) and previousupdatedtime (the capture before that). The keyword part has keyworddata.keywordinfo.lastupdatedtime and a monthlysearches array. keywordoverview with includeserpinfo: true returns the same serpinfo.lastupdatedtime, at no extra cost.

Here's what I saw in responses I kept. These are small samples, not a benchmark:

| Call (US, English) | Fetched | SERP captured | Days old | Previous capture |

|---|---|---|---|---|

| ranked_keywords, 3 rows | 27.10.2026 | 30.07, 10.09, 15.09 | 89, 47, 42 | 76, 65, 64 days earlier |

| keywordoverview + serpinfo | 12.10.2026 | 30.07 | 74 | – |

On the volume side, the keywordinfo rows in the 27.10 response were updated between 13.09 and 15.09, and the newest month in monthlysearches was August 2026. Two other calls from October (keyword ideas, domain intersection) also had keywordinfo dates of 12–15.09. searchintent_info dates were from late April.

So in those samples, SERP positions were 6 to 13 weeks old and refreshed roughly every two months. Volumes were probably one Google Ads update behind: Google normally adds the previous month around mid-month, so September should have been out by 27.10. I didn't call the status endpoint that day to confirm it. That fits the issue's split. Labs is fine for finding ideas and competitors. It's not good enough for "did they overtake us last week".

There's also a free check of the whole database: GET /v3/dataforseolabs/status returns a dateupdate for the Google, Bing and Amazon databases, and the docs say it isn't charged. Keep in mind that a database update doesn't mean every row was refreshed that day. That's why the per-row dates are what matter.

Put the date on the screen from the row itself

Rather than guessing which columns are stale, show what the API says:

from datetime import date, datetime, timezone

def row_age_days(ts: str | None, today: date | None = None) -> int | None:
    """DataForSEO timestamps look like '2026-07-30 06:09:07 +00:00'."""
    if not ts:
        return None
    today = today or datetime.now(timezone.utc).date()
    return (today - date.fromisoformat(ts[:10])).days

def freshness(item: dict) -> dict:
    """One ranked_keywords item -> the dates worth showing next to it."""
    serp = item.get("ranked_serp_element") or {}
    kinfo = (item.get("keyword_data") or {}).get("keyword_info") or {}
    months = kinfo.get("monthly_searches") or []
    newest = max(((m["year"], m["month"]) for m in months if m.get("year")), default=None)
    return {
        "serp_as_of": (serp.get("last_updated_time") or "")[:10] or None,
        "serp_age_days": row_age_days(serp.get("last_updated_time")),
        "volume_as_of": (kinfo.get("last_updated_time") or "")[:10] or None,
        "volume_newest_month": f"{newest[0]}-{newest[1]:02d}" if newest else None,
    }

Then make one rule and stick to it. For example, a position older than 30 days is shown as an estimate and can't drive a "they beat you" alert until a live check confirms it.

Live checks only where a decision depends on them

The targets list is short, so checking it live is cheap. Prices from DataForSEO's pricing pages, read in October and November 2026:

| What | Standard queue | Live |

|---|---|---|

| Google organic SERP, per 10 results | $0.0006 | $0.002 |

| Google Ads search volume, per task of up to 1,000 keywords | $0.06 | $0.09 |

| Labs (most endpoints), per task + per row returned | – | $0.012 + $0.00012 |

200 target keywords checked once a month on the standard queue costs 200 × $0.0006 = $0.12. Weekly, that's about $0.52 a month. The same check live costs $0.40 per pass. Two limits are worth knowing. First, the price covers the first 10 results: if you want to see a competitor at position 35, depth: 100 multiplies the price by 10. Second, Google Ads live endpoints accept at most 12 requests per minute per account, so send one 1,000-keyword task, not 1,000 one-keyword tasks.

Monthly is enough for volumes. The docs say Google "generally" updates keyword data in the middle of the month, and Google Ads doesn't return the current month. GET /v3/keywordsdata/googleads/status is free and returns actualdata (whether last month is in yet) plus lastyearinmonthlysearches / lastmonthinmonthlysearches. Run the volume refresh the first time actualdata turns true in a month, not on a fixed date.

For positions, the standard queue fits a weekly cron: taskpost up to 100 tasks per call, with tag set to your target ID. Then poll GET /v3/serp/google/organic/tasksready (free) and fetch each finished task once:

import base64, json, os, urllib.request

API = "https://api.dataforseo.com/v3"
AUTH = "Basic " + base64.b64encode(
    f"{os.environ['DFS_LOGIN']}:{os.environ['DFS_PASSWORD']}".encode()).decode()

def call(method, path, body=None):
    req = urllib.request.Request(API + path, method=method,
        data=json.dumps(body).encode() if body is not None else None,
        headers={"Authorization": AUTH, "Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=60) as r:
        return json.load(r)

def post_targets(targets):  # [{"id": "t42", "keyword": "...", "location_code": 2840, "language_code": "en"}]
    for i in range(0, len(targets), 100):
        call("POST", "/serp/google/organic/task_post", [
            {"keyword": t["keyword"], "location_code": t["location_code"],
             "language_code": t["language_code"], "depth": 10, "tag": t["id"]}
            for t in targets[i:i + 100]])

def collect(domains):  # {"t42": "competitor.com", ...}
    ready = call("GET", "/serp/google/organic/tasks_ready")
    out = {}
    for task in ready.get("tasks") or []:
        for r in task.get("result") or []:
            if r.get("tag") not in domains:
                continue  # someone else's task on the same account
            got = call("GET", f"/serp/google/organic/task_get/regular/{r['id']}")
            res = ((got["tasks"][0].get("result")) or [{}])[0]
            want = domains[r["tag"]]
            def ours(d):
                d = (d or "").lower()
                return d == want or d.endswith("." + want)  # not "notcompetitor.com"
            pos = next((it["rank_group"] for it in res.get("items") or []
                        if it.get("type") == "organic" and ours(it.get("domain"))), None)
            out[r["tag"]] = {"position": pos, "checked_at": res.get("datetime")}
    return out

position: None means "not in the depth you paid for", not "not ranking". Show it as "> 10".

The URL status check from the follow-up

Every URL that comes out of Labs or Search Console has a date of its own, and a page can be redirected or deleted since then. A HEAD request with no redirect follow is the right primitive. A few servers get HEAD wrong, though, so fall back to a 1-byte GET:

import time, urllib.error, urllib.request
from urllib.parse import urljoin

class NoRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, *a, **k):
        return None  # hand 3xx back to us instead of following it

OPENER = urllib.request.build_opener(NoRedirect)
UA = {"User-Agent": "my-seo-tool url-check (contact: you@example.com)"}

def check(url, cache, max_age_s=7 * 86400):
    hit = cache.get(url)
    if hit and time.time() - hit["at"] < max_age_s:
        return hit
    status, target = None, None
    for method, extra in (("HEAD", {}), ("GET", {"Range": "bytes=0-0"})):
        req = urllib.request.Request(url, method=method, headers={**UA, **extra})
        try:
            with OPENER.open(req, timeout=10) as r:
                status = r.status
        except urllib.error.HTTPError as e:
            status = e.code
            if 300 <= e.code < 400:
                target = urljoin(url, e.headers.get("Location", ""))
        except (urllib.error.URLError, TimeoutError):
            status = "unreachable"
        if status not in (405, 501, 403):  # HEAD refused or blocked: retry once with GET
            break
    hit = {"status": status, "target": target, "at": time.time()}
    cache[url] = hit
    return hit

Notes from running checks like this:

  • A 206 from the Range GET means the page is up. Treat it like a 200.
  • A 403 on both methods is usually a bot filter, not a missing page. Show it as "blocked", not as an error.
  • One 301 hop is enough to show the target. Don't chase chains here: the next crawl will.
  • Go easy on competitor sites. One request at a time per host, a second or two apart, and the 7-day cache means the same URL isn't checked on every page load.

What this doesn't solve

Live SERPs come from one location and one device per call, so they won't match what someone sees in another city or logged in. Google Ads volumes are rounded buckets for low-volume terms, so a "change" from 210 to 260 can be noise. Search Console is still the only real source for your own site. The rest is two kinds of estimate: one with a date on it, and one you paid a fraction of a cent to refresh.
