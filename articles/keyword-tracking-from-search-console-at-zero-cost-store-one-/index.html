Keyword tracking from Search Console at zero cost: store one row per day, then match your keyword list loosely

2026-11-11

A GitHub issue opened on 11.11.2026 asks for a no-cost design for keyword tracking built on Google Search Console. Two sites, 31 target keywords. The current setup keeps aggregated 7/28/90-day snapshots and only three of them per combination, so there's no real trend. And 0 of the 31 keywords match a GSC query exactly. The author is already careful: GSC "position" is an average and not a SERP rank, a missing match doesn't mean "not ranking", and legacy rows with position=0 shouldn't be shown. Here's how I'd fix the history and the matching without paying for anything. At the end there's a cost estimate for exact SERP checks, for the day someone asks for them.

1. Stop storing windows, store days

A 7/28/90-day window is an aggregate, so you can't get a daily series back out of three of them. The Search Analytics API will give you each day separately if you ask for one day at a time. Search Console keeps about 16 months of data, so you can backfill 16 months today instead of waiting for history to build up.

One call per site per day, with startDate == endDate:

# pip install google-api-python-client google-auth
from datetime import date, timedelta
from google.oauth2 import service_account
from googleapiclient.discovery import build

creds = service_account.Credentials.from_service_account_file(
    "sa.json", scopes=["https://www.googleapis.com/auth/webmasters.readonly"])
gsc = build("searchconsole", "v1", credentials=creds, cache_discovery=False)

def day_rows(site: str, day: date, dimensions: list[str]) -> list[dict]:
    rows, start = [], 0
    while True:
        body = {
            "startDate": day.isoformat(), "endDate": day.isoformat(),
            "dimensions": dimensions,  # e.g. ["query"] or ["query", "page"]
            "type": "web",
            "dataState": "final",      # the default; skips days that are still moving
            "rowLimit": 25000, "startRow": start,
        }
        resp = gsc.searchanalytics().query(siteUrl=site, body=body).execute()
        batch = resp.get("rows", [])
        rows += batch
        if len(batch) < 25000:
            return rows
        start += 25000

# Domain property: "sc-domain:example.es"; URL-prefix property: "https://example.es/"

To give the script access, add the service account's e-mail as a user of the property (Settings, Users and permissions, Restricted is enough). No billing account is needed, and at one or two calls per day per site you won't get anywhere near the API quotas.

For the daily job, re-fetch the last 5 or 6 days on every run and upsert. Final data usually shows up 2 to 3 days late, and re-fetching makes the job idempotent: a run that fails costs you nothing.

I'd store two grains, because they answer different questions and their numbers don't add up to each other:

  • dimensions: ["query"] (aggregated by property): "how does the site do for this query". Use this one for tracking.
  • dimensions: ["query", "page"] (aggregated by page): "which URL is showing". Its position and impressions are counted per page, so don't sum them back into query-level numbers.

Plus a third, tiny call with dimensions: ["date"] and no query. It gives you the property's real daily totals, which you'll need in section 3.

A schema proposal, in the "SQL only, not applied" spirit of the issue:

create table gsc_query_daily (
  site        text    not null,
  day         date    not null,
  query       text    not null,
  clicks      integer not null,
  impressions integer not null,
  position    numeric not null,          -- GSC average position for that day
  fetched_at  timestamptz not null default now(),
  primary key (site, day, query)
);

create table gsc_site_daily (             -- totals without the query dimension
  site text not null, day date not null,
  clicks integer not null, impressions integer not null,
  primary key (site, day)
);

Weekly position has to be weighted by impressions. A plain avg(position) lets a day with 1 impression at position 40 count as much as a day with 60 impressions at position 6:

select site, query, date_trunc('week', day) as week,
       sum(impressions) as impressions, sum(clicks) as clicks,
       round(sum(position * impressions) / nullif(sum(impressions), 0), 1) as avg_position
from gsc_query_daily
group by 1, 2, 3;

2. Why 0 of 31 match, and how to match without lying

Exact matching on lower(trim(keyword)) fails for boring reasons, especially in Spanish. People type without accents ("traduccion simultanea"), drop prepositions ("alquiler equipos traduccion"), reorder words, or add a city. A catalog written by a human uses the tidy form, and real queries rarely look like that.

I'd keep the catalog untouched and add a match type next to each observed query:

import re, unicodedata

STOP = {"de", "del", "la", "el", "los", "las", "para", "en", "y", "a", "con"}

def norm(s: str) -> str:
    s = unicodedata.normalize("NFKD", s.lower())
    s = "".join(c for c in s if not unicodedata.combining(c))
    return re.sub(r"\s+", " ", re.sub(r"[^\w\s]", " ", s)).strip()

def tokens(s: str) -> frozenset:
    return frozenset(t for t in norm(s).split() if t not in STOP)

def match_type(keyword: str, query: str) -> str | None:
    if query.strip().lower() == keyword.strip().lower():
        return "exact"
    if norm(query) == norm(keyword):
        return "normalized"   # accents, case, punctuation
    if tokens(keyword) and tokens(keyword) <= tokens(query):
        return "contains_all_words"   # word order, extra words like a city
    return None

For each catalog keyword, the screen shows the queries that matched, grouped by match type, with impressions, clicks and weighted position. A keyword with no matching query in the last 28 days gets the no_observada status, and the label should say exactly what it means: "no impressions recorded for a matching query in this period". It doesn't mean "doesn't rank". The page may sit on page 3, where almost nobody looks, or the query may be too rare to be reported (next section).

If you'd rather push part of the matching to the API, dimensionFilterGroups supports contains, equals, notContains, notEquals, includingRegex and excludingRegex (RE2). For example, {"dimension": "query", "operator": "includingRegex", "expression": "traducci(o|ó)n"} pulls the accented and unaccented spellings in one call. I still prefer fetching everything and matching locally: it's one call either way on a small site, and you can change the rules without fetching again.

3. Measure the hidden part instead of guessing it

Search Console leaves out queries that were searched by very few people, for privacy. Those impressions still count in the property totals, but they have no row when you group by query. On a small B2B site with niche, local queries, this can be a big share of the traffic. That's one more reason a 31-keyword catalog finds few matches.

You can measure it for free with the two tables above:

select s.site, s.day, s.impressions as total_impressions,
       coalesce(sum(q.impressions), 0) as impressions_with_query,
       round(100.0 * (s.impressions - coalesce(sum(q.impressions), 0))
             / nullif(s.impressions, 0), 1) as hidden_pct
from gsc_site_daily s
left join gsc_query_daily q on q.site = s.site and q.day = s.day
group by s.site, s.day, s.impressions;

Show that percentage on the dashboard. If 60 % of impressions are hidden, the keyword view is a partial sample, and the reader should know that before they read "no_observada" as bad news.

Two more display rules I'd add, as my own rule of thumb rather than anything official:

  • Don't show week-over-week position changes for a query with fewer than ~20 impressions in the week. An average over 3 impressions jumps around for no reason.
  • Filter by country when the business is local. Values are ISO 3166-1 alpha-3 codes (Spain is ESP; rows come back in lowercase, esp). Otherwise impressions from other countries skew the average position.

4. If exact SERP positions are ever approved: what it costs

GSC can't tell you "position 4 on mobile in Madrid today". For that you need a SERP API, and the bill is simply keywords × devices × checks per month × price per request. In my own measurements this month on DataForSEO, one Google top-10 request cost about $0.0015 in its priority queue and $0.0023 in live mode (prices change, check before you budget):

| Scope | Requests/month | At $0.0015 | At $0.0023 |

|---|---|---|---|

| 10 key keywords, desktop + mobile, weekly | 10 × 2 × 4.3 ≈ 86 | ≈ $0.13 | ≈ $0.20 |

| All 31, desktop + mobile, weekly | 31 × 2 × 4.3 ≈ 267 | ≈ $0.40 | ≈ $0.61 |

| All 31, desktop + mobile, daily | 31 × 2 × 30 = 1,860 | ≈ $2.79 | ≈ $4.28 |

With a per-search plan from another provider (the issue mentions SerpAPI), compare the same request count to the plan's monthly allowance. Whatever the provider, a SERP check is one sample, at one moment, from one location. Weekly checks of a short list against a fixed location (Spain, Spanish, plus the city if the business is local) usually say more than daily checks of everything. Store those rows in their own table with a source column, so they never get mixed up with GSC averages or the legacy position=0 rows.

What I'd ship first

1. Backfill 16 months of gscquerydaily and gscsitedaily, then a daily job that re-fetches the last 6 days.

2. The catalog view with match type, weighted weekly position, no_observada worded exactly as above, and the hidden-impressions percentage.

3. Only then, if someone needs an exact rank, a short weekly SERP list with its cost written next to it.

What this doesn't do: GSC has no data for keywords where the site gets no impressions. To see the demand you're missing entirely, you need search volumes. Google Ads' Keyword Planner gives free ranges if you have an Ads account; exact monthly numbers come from paid keyword data, which is a separate question.
