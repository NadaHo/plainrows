A daily rank tracker that survives load in Django and Celery: one task per keyword, one row per day, a quota on manual c

2026-11-13

A GitHub issue opened on 13.11.2026 lists why a Django + Celery rank tracker won't hold up under real load. The daily task checks every keyword one after another in a single task. It never sleeps, so it bursts requests at Google. A few hundred keywords hit the 30-minute CELERYTASKTIMELIMIT. Error snapshots count as "checked today", so a failed keyword waits until tomorrow. updateorcreate(..., recordedat=now) adds a new row on every retry. And POST /keywords/<id>/check/ has no quota or cooldown, so scraping and DataForSEO costs have no ceiling. The issue already has the right fix list. Here's the code I'd write for each item, tested, plus the cost numbers that decide most of it.

The setup in the repository: Django 4.2, Celery 5, Redis as broker, USETZ = True with TIMEZONE = "UTC". DataForSEO serp/google/organic/live/advanced comes first, at depth 100, with a direct Google scraper as fallback.

1. One row per keyword per day, enforced by the database

The current unique constraint includes recorded_at, a timestamp, so it never matches twice. Add a date column and put the constraint on it:

# models.py (KeywordRanking)
recorded_on = models.DateField(db_index=True)  # UTC day of the observation

class Meta:
    constraints = [
        models.UniqueConstraint(
            fields=["keyword", "search_engine", "country", "language", "device", "recorded_on"],
            name="one_ranking_per_keyword_per_day",
        )
    ]

Rows already in the table can break the new constraint, so the migration runs in three steps: add the field as null=True, then a RunPython that fills it and removes the duplicates, then make it non-null and swap the constraints. The RunPython step keeps the newest row of each day, except that an error never replaces a real answer:

def fill_and_dedupe(apps, schema_editor):
    KR = apps.get_model("seo", "KeywordRanking")
    keep, drop, batch = {}, [], []
    for r in KR.objects.order_by("recorded_at", "id").iterator(chunk_size=2000):
        r.recorded_on = r.recorded_at.date()  # UTC day: USE_TZ=True, TIME_ZONE="UTC"
        batch.append(r)
        k = (r.keyword_id, r.search_engine, r.country, r.language, r.device, r.recorded_on)
        prev = keep.get(k)
        if prev is None:
            keep[k] = (r.pk, r.result_status)
        elif r.result_status == "error" and prev[1] != "error":
            drop.append(r.pk)        # a later error never replaces a real answer
        else:
            drop.append(prev[0])     # otherwise the latest row of the day wins
            keep[k] = (r.pk, r.result_status)
        if len(batch) == 2000:
            KR.objects.bulk_update(batch, ["recorded_on"])
            batch = []
    KR.objects.bulk_update(batch, ["recorded_on"])
    for i in range(0, len(drop), 500):
        KR.objects.filter(pk__in=drop[i:i + 500]).delete()

The service then writes through one function. A failed retry can no longer overwrite the position you already have for today:

def save_daily_snapshot(keyword, result, now=None):
    now = now or timezone.now()
    key = dict(keyword=keyword, search_engine=keyword.search_engine, country=keyword.country,
               language=keyword.language, device=keyword.device,
               recorded_on=timezone.localdate(now))
    values = dict(position=result.position, ranking_url=result.url, title=result.title or "",
                  result_status=result.status, error_message=result.error_message or "",
                  search_domain=keyword.search_domain or "google.com.et", recorded_at=now)
    with transaction.atomic():
        snap, created = (KeywordRanking.objects.select_for_update()
                         .get_or_create(**key, defaults=values))
        if created:
            return snap
        if result.status == RankingResultStatus.ERROR and snap.result_status != RankingResultStatus.ERROR:
            return snap  # keep today's real answer, drop the failed retry
        for field, value in values.items():
            setattr(snap, field, value)
        snap.save(update_fields=list(values))
        return snap

If two workers create the same row at once, one of them gets the IntegrityError. Django's getorcreate catches it and reads the row the other worker wrote. So the constraint is the real guarantee, not the Python code.

2. "Done today" means a real answer

from django.db.models import Exists, OuterRef

DONE = [RankingResultStatus.FOUND, RankingResultStatus.NOT_FOUND]

def keywords_to_check(today):
    done_today = KeywordRanking.objects.filter(
        keyword=OuterRef("pk"), recorded_on=today, result_status__in=DONE)
    return (Keyword.objects.filter(is_active=True)
            .annotate(done=Exists(done_today)).filter(done=False)
            .select_related("project__owner"))

That's one query instead of one exists() per keyword. A keyword whose only row today is an error is still "to do".

3. Fan out: the beat task only enqueues

@shared_task(name="apps.seo.tasks.run_daily_rank_checks")
def run_daily_rank_checks():
    today, allowed, queued = timezone.localdate(), {}, 0
    for kw in keywords_to_check(today).iterator():
        owner = kw.project.owner
        if owner.pk not in allowed:  # one entitlement check per owner, not per keyword
            allowed[owner.pk] = PlanEntitlementService.can_use_feature(owner, FeatureCode.RANK_TRACKING)
        if allowed[owner.pk]:
            check_keyword_daily.delay(kw.pk)
            queued += 1
    return {"date": str(today), "queued": queued}


class TransientSerpError(Exception):
    pass


@shared_task(bind=True, name="apps.seo.tasks.check_keyword_daily",
             autoretry_for=(TransientSerpError,), retry_backoff=60, retry_backoff_max=1800,
             retry_jitter=True, max_retries=4, acks_late=True,
             soft_time_limit=120, time_limit=150)
def check_keyword_daily(self, keyword_id):
    kw = Keyword.objects.select_related("project").get(pk=keyword_id)
    if not keywords_to_check(timezone.localdate()).filter(pk=kw.pk).exists():
        return "already done"            # a duplicate message or a manual check got there first
    snap = RankTrackerService().check_keyword(kw)  # now saves through save_daily_snapshot
    if snap.result_status == RankingResultStatus.ERROR:
        raise TransientSerpError(snap.error_message[:200])  # retried after a random 0-1, 0-2, 0-4, 0-8 min
    return snap.result_status

The enqueuing task takes seconds whatever the keyword count. Each check has its own two-minute limit, so the 30-minute limit stops mattering. Add a second beat entry a few hours after the first, calling the same rundailyrank_checks. Because "done" means a real answer, it only picks up what failed all its retries. I'd keep it at two passes a day: a keyword that is still failing after that is a problem to look at, not one to keep paying for.

4. Throttle the part that needs it, and know what rate_limit= does

Celery's rate_limit="30/m" applies per worker instance, not globally. Celery's docs say so, and it's easy to miss. Four workers at 30/m make 120 calls a minute. For a limit across all workers, count in Redis:

import time
import redis
from django.conf import settings

_redis = redis.Redis.from_url(settings.CELERY_BROKER_URL)

def take_slot(name, per_minute):
    """Global across all workers: at most per_minute calls in the current clock minute."""
    key = f"ratelimit:{name}:{int(time.time() // 60)}"
    n = _redis.incr(key)
    if n == 1:
        _redis.expire(key, 120)
    return n <= per_minute

Call it right before the direct Google fetch, not around the whole check. When there's no slot, return an error result ("throttled"). The task's backoff retries it, with growing random delays. It's a fixed window, so a burst at a minute boundary can reach twice the limit for a moment. For a scraper fallback, that's acceptable.

Two limits to be honest about. DataForSEO's live endpoint accepts thousands of calls a minute, so you don't throttle it for the provider's sake: the only reason to pace those calls is your budget. And a direct scraper that hits Google from one server IP gets CAPTCHAs sooner or later, however slowly you pace it. I would turn the fallback off for the scheduled run and keep it, if at all, for occasional manual checks. A pacing limit makes blocks less frequent. It doesn't stop them.

5. Manual checks: a cooldown per keyword and a daily quota per user

With Django's cache. It has to be a shared cache: the project's settings have no CACHES, which means the per-process local-memory cache, so every worker would have its own counters. Django 4.2 ships django.core.cache.backends.redis.RedisCache, so you can point it at the same Redis.

from datetime import datetime, timedelta, timezone as dt_timezone
from django.core.cache import cache
from django.utils import timezone

COOLDOWN_S = 15 * 60
DAILY_MANUAL = {"starter": 20, "agency": 100}

def manual_check_refusal(user_id, plan, keyword_id):
    """None if allowed, else (reason, retry_after_seconds)."""
    if not cache.add(f"rank:cooldown:{keyword_id}", 1, COOLDOWN_S):
        return "cooldown", COOLDOWN_S
    today = timezone.localdate()
    key = f"rank:manual:{user_id}:{today.isoformat()}"
    cache.add(key, 0, 2 * 86400)
    if cache.incr(key) > DAILY_MANUAL.get(plan, 0):
        tomorrow = datetime.combine(today + timedelta(days=1), datetime.min.time(), tzinfo=dt_timezone.utc)
        return "daily_quota", int((tomorrow - timezone.now()).total_seconds())
    return None

In check_ranking, after the entitlement check: if this returns a refusal, answer 429 with a Retry-After header and don't enqueue anything. cache.add only writes when the key is missing, so two quick clicks give one check. incr is atomic on Redis. The cooldown is reported as the full 15 minutes, a slight overestimate that the client can live with. The plan names and numbers are placeholders: take them from the plan model you already use for keyword quotas.

6. The cost numbers that decide the rest

DataForSEO bills Google organic per page of 10 results, rounded up, and refunds the difference when Google returns fewer than you asked for. At depth 100, that's 10 pages per check. The prices on their pricing page today (11.2026), for one keyword checked once a day:

| Mode | Per check at depth 100 | 300 keywords / day | 300 keywords / 30 days |

|---|---|---|---|

| Live | $0.020 | $6.00 | $180 |

| Priority queue | $0.012 | $3.60 | $108 |

| Standard queue | $0.006 | $1.80 | $54 |

| Standard queue, depth 20 | $0.0012 | $0.36 | $10.80 |

Two choices matter more than any throttle:

  • Depth. The model stores "not in top 100", but if the dashboard shows "not in the top 20" past page 2, depth 20 costs a fifth as much. Decide it per plan.
  • Queue instead of live for the daily run. A scheduled job doesn't need an answer within seconds. serp/google/organic/taskpost takes up to 100 tasks per request, with a tag (put the keyword id there). tasksready lists the finished ones, and taskget/advanced/{id} returns the same result as live at less than a third of the price. The beat task posts. A second periodic task every few minutes collects what's ready and saves it through savedaily_snapshot. Keep live for the manual button, where someone is waiting.

Whatever you choose, read the cost field each response returns and add it to a daily total per plan. That's the number to compare with what the plan brings in, and to cut off when something loops.

What I tested, and what I didn't

I ran the migration function, savedailysnapshot, keywordstocheck and manualcheckrefusal against Django 4.2.11 on SQLite, with the local-memory cache standing in for Redis. Six rows over two days dedupe to one per day: the later success wins over a later error, and the last error stays on a day with no success. Error, success, then error on the same day leaves one row holding the success. The quota refuses the 21st check of a starter user, and the cooldown refuses a second click on the same keyword. I checked that Celery 5.7 accepts the task options and schedules a jittered retry when the error is raised, and I ran the Redis counter against a fake client (3 of 5 calls pass at per_minute=3). I didn't run anything against the project's real database, a real Redis or a live DataForSEO account. The prices come from DataForSEO's public pricing page as of 13.11.2026.
