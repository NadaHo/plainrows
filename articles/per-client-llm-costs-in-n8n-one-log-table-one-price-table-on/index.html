Per-client LLM costs in n8n: one log table, one price table, one query

2026-11-02

A question that keeps coming up on the n8n forum: you build automations for several clients on one OpenAI or Anthropic account, and at month end you need to know what each client cost. Here's a setup that holds up with shared sub-workflows, cached tokens and retries.

1. Tag the client at the entry point

Every workflow a client triggers sets a client_id in its first node. Sub-workflows receive it as a declared input on the "When Executed by Another Workflow" trigger. Don't infer the client from the workflow name: the name stops identifying the client as soon as two clients share a sub-workflow.

2. Log the real token counts

When you call the model through an HTTP Request node, the response contains the billed counts:

| Provider | Fields |

|---|---|

| OpenAI Chat Completions | usage.prompttokens, usage.completiontokens, usage.prompttokensdetails.cached_tokens |

| OpenAI Responses | usage.inputtokens, usage.outputtokens, usage.inputtokensdetails.cached_tokens |

| Anthropic Messages | usage.inputtokens, usage.outputtokens, usage.cachereadinputtokens, usage.cachecreationinputtokens |

The AI Agent and chat model sub-nodes don't expose usage to the main flow. A separate scheduled workflow can read finished executions through the n8n API (GET /api/v1/executions?includeData=true) and sum the tokenUsage / tokenUsageEstimate objects of the model sub-node's runs. The estimate is n8n's count, not the provider's, so flag those rows as approximate.

Normalise the counts before storing them. OpenAI's prompttokens includes cached tokens, while Anthropic's inputtokens excludes both cache reads and cache writes:

create table llm_usage (
  call_id        text primary key,  -- provider response id
  ts             timestamptz not null,
  client_id      text not null,
  workflow       text,
  execution_id   text,
  model          text,
  input_uncached int,  -- OpenAI: prompt_tokens - cached_tokens | Anthropic: input_tokens
  cache_read     int,  -- OpenAI: cached_tokens                  | Anthropic: cache_read_input_tokens
  cache_write    int,  -- OpenAI: 0                              | Anthropic: cache_creation_input_tokens
  output_tok     int
);

Using the response id as primary key means a log step that runs twice can't double-count. A retried call that succeeded has a new id and appears again, which matches what the provider bills. A call that failed with an HTTP error returns no usage and costs nothing.

3. Apply prices at month end

Keep prices in a table with validfrom / validto so a price change doesn't rewrite past months:

select u.client_id,
       date_trunc('month', u.ts) as month,
       round(sum( u.input_uncached * p.in_per_m
                + u.cache_read     * p.cache_read_per_m
                + u.cache_write    * p.cache_write_per_m
                + u.output_tok     * p.out_per_m ) / 1e6, 2) as usd
from llm_usage u
join prices p
  on p.model = u.model
 and u.ts >= p.valid_from
 and (p.valid_to is null or u.ts < p.valid_to)
group by 1, 2
order by 1, 2;

Compare the monthly total with the provider invoice. The gap is usage that doesn't go through n8n (scripts, the playground, someone else's agent on the same key). Close it before invoicing from this table.

4. Catch runaways within the hour

A workflow can't reliably stop a loop it is itself running. The hard stop is a budget limit at the provider, ideally one project or key per client. On top of that, an hourly query that compares calls per client and workflow with their usual hourly count, and alerts at about 3x, catches a retry storm the same hour.

Limits

  • tokenUsageEstimate rows are estimates. If a client's invoice depends on them, move that client's calls to HTTP Request nodes.
  • Per-minute voice costs are a different unit. Put them on their own invoice line rather than converting them into tokens.
  • This tells you what each client cost, not whether to pass it through or charge a flat fee. A flat fee works for small, steady spend. Spend that can double in a month is easier to defend as pass-through with this breakdown attached.
