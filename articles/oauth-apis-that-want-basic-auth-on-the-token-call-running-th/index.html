OAuth APIs that want Basic auth on the token call: running the token flow yourself in Make

2026-11-03

Some OAuth 2.0 providers refuse client credentials in the body of the token request. They want Authorization: Basic base64(clientid:clientsecret) on /oauth/token and nothing else. Bling ERP (API v3) is one of them, and a question on the Make forum this week ran into it: the consent screen works, then the connection fails with invalid_client.

The generic OAuth 2.0 connection of Make's HTTP > Make a request module lets you add extra body parameters to the token and refresh requests. It also has a Custom Headers field, but the docs don't say whether those headers go on the token call. Try a static Authorization: Basic ... header there first. If the provider still answers invalid_client, handle the tokens yourself. It takes three scenarios and a data store.

The pieces

| Piece | What it does |

|---|---|

| Data store tokens | one record: accesstoken, refreshtoken, expires_at |

| Callback scenario (instant, always on) | Custom webhook = the app's redirect URL; exchanges the code for tokens and saves them |

| Refresh scenario (scheduled) | exchanges the refresh token for new tokens before the access token expires |

| Your API scenarios | read the access token and send Authorization: Bearer ... |

Callback scenario

1. Custom webhook. Register its URL as the redirect URL in the provider's developer settings.

2. HTTP > Make a request.

- Authentication type: Basic Auth, with a keychain where username = client ID and password = client secret. Make encodes the header.

- POST to the token URL, body application/x-www-form-urlencoded: granttype=authorizationcode, code={{1.code}}, plus redirect_uri if the provider requires it.

- Parse response: yes.

3. Data store > Add/replace a record with expiresat = {{addSeconds(now; 2.data.expiresin)}}.

4. Webhook response with a short "connected" page.

Keep this scenario on before you open the authorization link. Authorization codes are short-lived. Bling's expire after 30 seconds, so copying one by hand into a module is too slow. If you send a state value, check it with a filter right after the webhook.

Refresh scenario

Schedule it a bit inside the access token's lifetime. For Bling, the access token lasts 6 hours (expiresin: 21600) and the refresh token 30 days, so every 5 hours works. Same HTTP module, with granttype=refreshtoken and refreshtoken={{record.refresh_token}}. Save both tokens from the response. Many providers rotate the refresh token, and the old one may stop working once it's used.

Refresh from one scenario only. Two scenarios refreshing with the same refresh token at the same moment is the classic way to end up logged out.

Calling the API

Get the record, then HTTP > Make a request with Authentication type "No authentication" and a header Authorization: Bearer {{record.access_token}}.

Provider-specific headers

Read the token section of the provider's docs once more before building. Bling, for example, has deprecated its opaque tokens. To get JWTs you add enable-jwt: 1 to every token and refresh request. If you forget it on the refresh call, you silently fall back to the old kind.

Limits

  • Tokens sit in a data store. Turn on "Data is confidential" in the scenario settings so they don't appear in execution history, and limit who can open the data store.
  • If the refresh scenario stops for longer than the refresh token's lifetime (30 days for Bling), someone has to click the authorization link again. A failure alert on the refresh scenario is worth adding.
  • A scheduled refresh costs a few runs a day even when nothing else happens. On a small plan, refresh on demand instead: check expires_at at the start of each API scenario and refresh only when it is close.
  • This is one connection for one account. For many end users you need one record per user, keyed by something you get back in state.
