Asking DataForSEO for gzip: why the body can arrive still compressed, and a check that works everywhere

2026-11-04

DataForSEO compresses its responses when the request says Accept-Encoding: gzip, and the savings are large. One open-source SEO project measured the US location list at about 9.9 MB uncompressed and 0.6 MB with gzip. Their 04.11.2026 bug report shows the catch: in one runtime, the body reached JSON.parse still compressed and every call failed with Unexpected token '\x1f'.

What happens in each runtime

I tested this with a local server that always answers gzip with Content-Encoding: gzip:

| Client | Body you get | Content-Encoding afterwards |

|---|---|---|

| workerd (2026-11-04), header set or not | decoded | still gzip |

| Node 22 fetch, header set or not | decoded | still gzip |

| Python urllib with the header set | compressed (1f 8b) | gzip |

| curl with the header but without --compressed | compressed | gzip |

| celld (denoland/celld#238, reported, not tested by me) | compressed | gzip |

Two things follow:

1. "The runtime decodes gzip for me" depends on the runtime. Low-level clients (urllib, plain curl) never decode, and at least one Workers-compatible runtime doesn't either.

2. You can't rely on the header to decide. workerd and Node decode the body and keep Content-Encoding: gzip, so "header says gzip, decompress it" breaks on the runtimes that work, and "trust the runtime" breaks on the ones that don't.

A check that works everywhere

A JSON body starts with {, [ or whitespace, never with the gzip magic bytes 1f 8b. So check the bytes:

async function readJsonText(response: Response): Promise<string> {
  const bytes = new Uint8Array(await response.arrayBuffer());
  if (bytes.length >= 2 && bytes[0] === 0x1f && bytes[1] === 0x8b) {
    const decoded = new Blob([bytes]).stream().pipeThrough(new DecompressionStream("gzip"));
    return await new Response(decoded).text();
  }
  return new TextDecoder().decode(bytes);
}

I ran this in workerd and in Node 22 with a gzipped JSON body (with non-ASCII characters), a plain body and an empty body, and it returned the original string each time. Read the bytes with arrayBuffer(), not text(). Once the bytes have gone through text(), the 8b byte is replaced by U+FFFD, which is why the log in that bug report shows 1f ef bf bd 08, and you can't reliably get the original bytes back.

The same check in Python, where urllib never decodes:

import gzip, json, urllib.request

# url and auth (your "Basic ..." header value) defined elsewhere
req = urllib.request.Request(url, headers={"Accept-Encoding": "gzip", "Authorization": auth})
raw = urllib.request.urlopen(req, timeout=60).read()
data = json.loads(gzip.decompress(raw) if raw[:2] == b"\x1f\x8b" else raw)

(requests and httpx decode gzip on their own. The check costs nothing there and protects you if you switch clients.)

Limits

  • This buffers the whole body, so the compressed and decoded copies sit in memory together. That's fine at 10 MB. For very large responses (Lighthouse, big SERP batches), stream through DecompressionStream instead of reading everything first.
  • Brotli (br) has different magic bytes and isn't supported by DecompressionStream everywhere. If you only ask for gzip, you only get gzip.
  • Don't retry a billed call because parsing failed: the request reached DataForSEO and was charged. Fix the decoding and parse the body you already have.
