A weekly Google Maps geo-grid rank check for restaurants: grid math, place matching, and the real cost per location

2026-11-12

A GitHub issue opened on November 11, 2026 plans keyword rank tracking for restaurant websites. Owners want to know "do we show up when someone nearby searches 'shawarma near me' or 'best brunch in Olaya'?". The plan: up to 10 keywords per location, a weekly check of the location's position in Google Maps results at the points of a 5 × 5 grid spaced 1 km apart, "not in the top 20" instead of 0, a baseline check when the site is first published, and a monthly budget per organization. The data provider is still "vendor to pick". I build this kind of check myself, so here's the part the issue leaves open: how to generate the grid, how to know that a result is *your* restaurant, what one weekly check costs, and what a grid can't tell you.

1. The grid

A grid point is just a coordinate. At each one you ask Google Maps for the keyword as if the searcher stood there. One degree of latitude is about 111.32 km everywhere. One degree of longitude shrinks with the cosine of the latitude (about 101 km at Riyadh's 24.7° N). So:

// grid.ts — weekly geo-grid check on Google Maps. Node 18+ or a Worker (fetch, btoa).
const KM_PER_DEG_LAT = 111.32;

export type Point = { row: number; col: number; lat: number; lng: number };

/** n x n points around (lat, lng), spacingM apart; row 0 = north, col 0 = west. */
export function gridPoints(lat: number, lng: number, n = 5, spacingM = 1000): Point[] {
  const half = (n - 1) / 2, km = spacingM / 1000, out: Point[] = [];
  for (let row = 0; row < n; row++)
    for (let col = 0; col < n; col++)
      out.push({
        row, col,
        lat: +(lat + ((half - row) * km) / KM_PER_DEG_LAT).toFixed(6),
        lng: +(lng + ((col - half) * km) / (KM_PER_DEG_LAT * Math.cos((lat * Math.PI) / 180))).toFixed(6),
      });
  return out;
}

I checked it with a haversine distance: for a 5 × 5 grid at 24.6951, 46.6853, neighbouring cells come out 998.8 m apart east-west and 998.9 m north-south. That's well inside what matters for a map grid. Row/col indexes are what the colored map needs, so keep them with every result.

2. One search per point, through a queue

Any SERP API that accepts a coordinate for Maps searches will do. I'll use DataForSEO's Google Maps endpoint as the example because its prices are public. One request = one point × one keyword. It takes location_coordinate as "lat,lng,zoom" (zoom 3z to 21z, 17z if omitted) and bills per result page of up to 100 places. Public prices today (11.2026):

| Mode | Per point | One weekly check (10 keywords × 25 points) | Per month (× 52 / 12) |

|---|---|---|---|

| Standard queue | $0.0006 | $0.15 | ≈ $0.65 |

| Priority queue | $0.0012 | $0.30 | ≈ $1.30 |

| Live | $0.002 | $0.50 | ≈ $2.17 |

That's per location. A weekly cron job doesn't need answers within seconds, so the standard queue is the right fit: post the tasks, collect them later. A tag on each task brings the check, keyword and grid cell back with the result:

export const PRICE_PER_SERP = { standard: 0.0006, priority: 0.0012, live: 0.002 }; // USD, up to 100 results each

/** Cost of one check, known before any call: compare it with what's left of the month's budget. */
export const checkCostUsd = (keywords: number, n: number, price = PRICE_PER_SERP.standard) =>
  keywords * n * n * price;

/** Task bodies for task_post (max 100 per request). */
export function tasksFor(checkId: string, keywordId: string, phrase: string, locale: "ar" | "en", pts: Point[], zoom = 15) {
  return pts.map((p) => ({
    keyword: phrase,
    location_coordinate: `${p.lat},${p.lng},${zoom}z`,
    language_code: locale,        // the keyword's own language, as the issue says
    depth: 20,                    // you only report the top 20; the price is the same up to 100
    tag: `${checkId}:${keywordId}:${p.row}:${p.col}`,
  }));
}

export async function postTasks(tasks: object[], login: string, password: string) {
  const auth = "Basic " + btoa(`${login}:${password}`);
  const ids: string[] = [];
  for (let i = 0; i < tasks.length; i += 100) {
    const res = await fetch("https://api.dataforseo.com/v3/serp/google/maps/task_post", {
      method: "POST",
      headers: { Authorization: auth, "Content-Type": "application/json" },
      body: JSON.stringify(tasks.slice(i, i + 100)),
    });
    const body: any = await res.json();
    for (const t of body.tasks ?? []) {
      if (t.status_code !== 20100) throw new Error(`task refused: ${t.status_code} ${t.status_message}`);
      ids.push(t.id);
    }
  }
  return ids;
}

The budget rule from the issue fits naturally here. The price of a check is known before you send anything (keywords × points × unit price), so the cron job compares checkCostUsd(...) with the rest of the organization's monthly budget and skips the whole check, with a reason, if it doesn't fit. Don't run half a grid: a grid with 12 points out of 25 isn't comparable with last week's. Count the baseline check at first publish in the same budget, plus a little room for re-posting failed cells.

Keep the zoom fixed. The zoom changes which places come back, so a history where the zoom changed halfway is two different measurements. Store zoom with every check, next to gridSize and spacingMeters.

3. Collecting, and knowing a result is yours

Receiving results is free. tasksready lists up to 1,000 finished tasks from the last three days (20 calls a minute), and taskget/advanced/{id} returns each one. An hourly cron tick that collects whatever is ready is enough. If you'd rather not poll, postback_url pushes results to an endpoint of yours. If other jobs share the same API account, skip any tag that doesn't start with one of your open check IDs before parsing it.

The important part is matching. Match on the place ID (or the CID), never on the name. Restaurant names repeat ("Shawarma House" can easily have three branches inside one grid), and names show up in Arabic or in English depending on the query language. So you need each location's Google place ID once, at setup. The cheapest reliable way: let the owner paste their Google Maps link, or run one Maps search for the restaurant's name at its own coordinates (one $0.0006 request) and have the owner confirm which result is theirs. Store it on OrganizationLocation.

/** Position of the location among the organic places of one result; null = not in the top 20. */
export function rankOf(items: any[] | null | undefined, placeId: string, cid?: string): number | null {
  const places = (items ?? []).filter((i) => i?.type === "maps_search").slice(0, 20);
  const i = places.findIndex((p) => p.place_id === placeId || (cid != null && p.cid === cid));
  return i === -1 ? null : i + 1;
}

/** One row per finished grid cell. Errors stay errors, never "not in the top 20".
 *  auth: the same "Basic ..." header as in postTasks. */
export async function collect(auth: string, placeOf: (keywordId: string) => { placeId: string; cid?: string }) {
  const base = "https://api.dataforseo.com/v3/serp/google/maps";
  const get = async (path: string) =>
    (await (await fetch(`${base}/${path}`, { headers: { Authorization: auth } })).json()) as any;
  const ready = await get("tasks_ready");
  const rows: { tag: string; rank: number | null; status: "ok" | "no_results" | "error" }[] = [];
  for (const t of ready.tasks?.[0]?.result ?? []) {
    const body = await get(`task_get/advanced/${t.id}`);
    const task = body.tasks?.[0];
    const tag: string = task?.data?.tag ?? t.tag;
    const { placeId, cid } = placeOf(tag.split(":")[1]);
    if (task?.status_code === 20000) rows.push({ tag, rank: rankOf(task.result?.[0]?.items, placeId, cid), status: "ok" });
    else if (task?.status_code === 40102) rows.push({ tag, rank: null, status: "no_results" });
    else rows.push({ tag, rank: null, status: "error" }); // re-post this cell, don't store it as "not in top 20"
  }
  return rows;
}

Two details in there are deliberate:

  • Only maps_search items are counted, so sponsored pins don't push your position down. Decide whether you want that, and say it in the UI.
  • A failed task is not "not found". If you store an error as "not in the top 20", one bad provider minute shows up as a ranking drop on the owner's dashboard. Re-post failed cells, and only close the check when all 25 have an answer. Code 40102 ("no search results") is a real empty answer: no places at all came back for that point.

On Workers, keep an eye on the subrequest limit per invocation (one fetch per task_get). Collect in batches across ticks rather than all at once.

I type-checked it with tsc --strict, ran the grid and cost functions, and ran collect against a mocked fetch that returned a saved real Maps response, a 40102 and a 50000. It returned rank 3, no_results and error, as intended. I didn't make a live call for this post.

4. The numbers on the dashboard

The issue already says "not in the top 20, never 0". The average still needs a convention, though, or an unranked point quietly vanishes from it:

/** Not found counts as 21 in the average, so weeks stay comparable. */
export function summarize(ranks: (number | null)[]) {
  const found = ranks.filter((r): r is number => r !== null);
  const avg = (xs: number[]) => (xs.length ? +(xs.reduce((a, b) => a + b, 0) / xs.length).toFixed(2) : null);
  return {
    averageRank: avg(ranks.map((r) => r ?? 21)),
    averageRankWhereFound: avg(found),
    foundPct: ranks.length ? Math.round((100 * found.length) / ranks.length) : null,
    top3Pct: ranks.length ? Math.round((100 * found.filter((r) => r <= 3).length) / ranks.length) : null,
  };
}

For ranks [1, 2, null, 5, null] this gives an average of 10 (counting misses as 21), 2.67 where found, found at 60 % of points, top 3 at 40 %. Owners usually understand the last one best: "you're in the top 3 at 10 of 25 points around your restaurant". I'd show it next to the map and add foundPct and top3Pct columns to SeoRankCheck instead of recomputing them from points every time.

What a grid doesn't tell you

  • It's a simulation. A coordinate stands in for the searcher's position, which is what "near me" depends on. But a real person on a phone, signed in, with a search history, can see a different order. Present the result as "what a searcher at this spot sees", not "what everyone sees".
  • One sample a week is noisy. Maps results move from day to day, so a change of one or two places in the average isn't news. Look at the trend over three or four checks before telling an owner something improved.
  • Google Maps results aren't the same as the map pack in normal Google Search. They're related but not identical. If the owner's question is really about the search results page, that's a different (organic/local) request.
  • For a few keywords, a free spot check still works: open Google Maps, search the keyword from the restaurant's neighbourhood, and look. The grid is worth paying for when you need history and many points.

For Part 1 of the issue, Google's structured data docs describe priceRange as either a numerical range ("$10-15") or a number of currency signs ("$$$"), shorter than 100 characters, or Google won't show it. In Riyadh, a range in the local currency (for example "SAR 40-80") is less ambiguous than dollar signs. servesCuisine is free text in schema.org, so the fixed key list with translations the issue describes is a good way to keep it consistent.
