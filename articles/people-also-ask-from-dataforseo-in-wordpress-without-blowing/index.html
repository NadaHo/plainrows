People Also Ask from DataForSEO in WordPress without blowing a 30-second request

2026-11-07

An issue opened on 06.11.2026 against an open-source WordPress FAQ generator points at a gap that a lot of plugins probably have. The plugin used to pull Google's People Also Ask (PAA) questions from DataForSEO's SERP API. The call was removed because it was "too slow (15s+ timeouts with 0 bytes)" and killed bulk runs on hosts with a 30-second limit. Since then the FAQ questions come only from two Labs keyword calls, while the ranking code still gives PAA the highest weight and the readme still promises real PAA questions.

You don't need another provider to get PAA back. The problem is that the plugin waits for a live SERP inside the same PHP request that does everything else. Here is how I'd do it instead.

What the live call costs, in money and seconds

DataForSEO's pricing page (read on 07.11.2026) gives three ways to get the same Google organic SERP, priced per SERP of up to 10 results:

| Mode | Price per SERP | Stated turnaround |

|---|---|---|

| Live (live/advanced, one request) | $0.002 | "up to 6 seconds on average" |

| Priority queue (taskpost + taskget) | $0.0012 | "up to 1 minute on average" |

| Standard queue (taskpost + taskget) | $0.0006 | "~5 minutes on average", target 45 minutes |

Those are averages, not upper bounds. One live call I recorded on 22.10.2026 ("crm software", US, English, depth 10) took 3.16 s and cost $0.002. It returned 4 PAA questions and 8 related searches. That's one call, not a benchmark. The "0 bytes" in the error is what cURL reports when its timeout runs out before the first byte of the answer arrives, so the plugin was hitting slow calls well past the average.

Now look at the whole request. In that generator, the two Labs calls have a 5 s timeout each and the LLM call has 25 s. That is already 35 s in the worst case before any SERP call. Whatever you set the SERP timeout to, a synchronous chain like that can't fit under 30 s on a bad day.

One detail worth checking on your own host: per the PHP manual, on Linux maxexecutiontime "only affect[s] the execution time of the script itself" and doesn't count things like stream operations. So the limit that actually cuts a request stuck on the network is often a wall-clock one: PHP-FPM's requestterminatetimeout, the web server's FastCGI or proxy timeout, or the host's own limit. The log tells you which one fired. A PHP fatal "Maximum execution time of 30 seconds exceeded" is not the same problem as a 504 from the proxy.

The fix: queue the SERP, collect it later

The task endpoints were made for this. You post the task in one short request, DataForSEO runs it, and a cron job picks up the result. As a bonus, on the Standard queue it costs less than a third of the live price. The flow:

1. When a post is queued for FAQ generation (one post or a bulk run), send one task_post with tag set to the post ID.

2. Every few minutes, WP-Cron calls tasksready. It's free, it returns up to 1,000 finished tasks from the last three days, and a task stays on the list until you collect it. Fetch only the tasks with your own tags from taskget/advanced and save the questions in post meta.

3. Generate the FAQ once the meta is there. If you don't want to wait, generate it without PAA and regenerate later.

function paa_dfs_request( string $method, string $url, ?array $body, int $timeout ) {
	$args = array(
		'method'  => $method,
		'timeout' => $timeout,
		'headers' => array(
			'Authorization' => 'Basic ' . base64_encode( get_option( 'my_dfs_login' ) . ':' . get_option( 'my_dfs_password' ) ),
			'Content-Type'  => 'application/json',
		),
	);
	if ( null !== $body ) {
		$args['body'] = wp_json_encode( $body );
	}
	$response = wp_remote_request( $url, $args );
	if ( is_wp_error( $response ) ) {
		return $response;
	}
	return json_decode( wp_remote_retrieve_body( $response ), true );
}

/** Pull PAA questions and related searches out of an "advanced" SERP result. */
function paa_from_serp_result( $result ): array {
	$out = array();
	foreach ( (array) ( $result['items'] ?? array() ) as $item ) {
		$type = $item['type'] ?? '';
		if ( 'people_also_ask' === $type ) {
			foreach ( (array) ( $item['items'] ?? array() ) as $el ) {
				if ( ! empty( $el['title'] ) ) {
					$out[] = array( 'question' => $el['title'], 'source' => 'paa' );
				}
			}
		} elseif ( 'related_searches' === $type ) {
			foreach ( (array) ( $item['items'] ?? array() ) as $query ) {
				if ( is_string( $query ) && '' !== $query ) {
					$out[] = array( 'question' => $query, 'source' => 'related_search' );
				}
			}
		}
	}
	return $out;
}

/** Step 1, in the editor or bulk request: queue one SERP task per post. */
function paa_queue( int $post_id, string $keyword, int $location_code, string $language_code ): bool {
	$body = paa_dfs_request( 'POST', 'https://api.dataforseo.com/v3/serp/google/organic/task_post', array(
		array(
			'keyword'       => $keyword,
			'location_code' => $location_code,
			'language_code' => $language_code,
			'depth'         => 10,
			'tag'           => 'faq-' . $post_id,
		),
	), 10 );
	if ( is_wp_error( $body ) ) {
		// Don't send it again blindly: the task may exist (and be billed) even if the answer was lost.
		return false;
	}
	$task = $body['tasks'][0] ?? array();
	if ( 20100 !== (int) ( $task['status_code'] ?? 0 ) ) { // 20100 = "Task Created."
		return false;
	}
	update_post_meta( $post_id, '_faq_paa_status', 'queued' );
	return true;
}

/** Step 2, from WP-Cron every few minutes: collect the finished tasks that are ours. */
function paa_collect(): int {
	$ready = paa_dfs_request( 'GET', 'https://api.dataforseo.com/v3/serp/google/organic/tasks_ready', null, 10 );
	if ( is_wp_error( $ready ) ) {
		return 0;
	}
	$done = 0;
	foreach ( (array) ( $ready['tasks'][0]['result'] ?? array() ) as $t ) {
		if ( ! preg_match( '/^faq-(\d+)$/', (string) ( $t['tag'] ?? '' ), $m ) || empty( $t['endpoint_advanced'] ) ) {
			continue; // not ours: leave it on the list for whoever posted it
		}
		$got = paa_dfs_request( 'GET', 'https://api.dataforseo.com' . $t['endpoint_advanced'], null, 15 );
		if ( is_wp_error( $got ) ) {
			continue; // retried on the next run if it is still listed
		}
		$task = $got['tasks'][0] ?? array();
		$code = (int) ( $task['status_code'] ?? 0 );
		if ( 20000 === $code ) {
			$questions = paa_from_serp_result( $task['result'][0] ?? array() );
		} elseif ( 40102 === $code ) { // "No Search Results."
			$questions = array();
		} else {
			continue;
		}
		update_post_meta( (int) $m[1], '_faq_paa', $questions );
		update_post_meta( (int) $m[1], '_faq_paa_status', 'done' );
		$done++;
	}
	return $done;
}

The output uses the same paa and relatedsearch source names the plugin's ranking already weights, so nothing else has to change. endpointadvanced in tasks_ready is a path starting with /v3/, which is why the host is prepended. Related searches come back as plain strings, while PAA questions are objects with a title.

What I tested, and how: the code ran on PHP 8.5 with stubbed WordPress functions and mocked HTTP, no paid call. Parsing the recorded live response gave the 4 PAA questions and 8 related searches. The queue step sent a one-task array tagged faq-42 and returned false on a 40200 "Payment Required" answer and on a timeout. The collector stored a finished task, stored an empty list for 40102, left a timed-out task for the next run and never fetched a task with someone else's tag. I haven't run it against the real API or inside a real WordPress install.

If it has to stay synchronous

Sometimes the FAQ has to come out of the same click. Then give the SERP call its own short timeout (8 to 10 s), treat a timeout as "no PAA this time" rather than a failed FAQ, and cache the questions in a transient keyed on keyword, location and language, so a bulk run over posts that share a focus keyword pays once. Also count the time of every call in the request against the wall-clock limit, not just this one.

Limits

  • Not every SERP has a PAA box. You still pay for the SERP when there is none, and you get no PAA questions from it. The peoplealsoaskclickdepth parameter (1 to 4) expands more questions for $0.00015 per click. Clicks that can't be performed are refunded.
  • PAA questions have no search volume. If your ranking uses volume as a tiebreaker, they need their own weight, which is what that plugin already does.
  • The Standard queue is an average of about 5 minutes with a 45-minute target, so "collect later" can mean most of an hour on a bad day. Priority costs twice as much and averages about a minute.
  • A post can stay queued for good: the task failed on DataForSEO's side, or a task_get timed out after the task was already marked as collected. Re-queue posts that are still queued after a day or so. That's another SERP to pay.
  • WP-Cron only runs when the site gets traffic. On a quiet site, trigger wp-cron.php from a real cron job.
  • tasksready is limited to 20 calls a minute and only lists tasks from the last three days. If you use postbackurl instead (results POSTed to your site, gzipped), those tasks don't appear in tasks_ready unless the postback failed. And your site needs a public URL that accepts them.
  • If a live call times out on your side, I'd count it as spent. I haven't found a statement in the docs either way on whether an abandoned live request is billed.
